# Prompt 模板参考

> 每个阶段对应的 Prompt 模板，直接复制到任意 Agent 对话框使用。
> 将 `[占位符]` 替换为你的实际内容。
> 标准开发流程：需求分析 → 方案设计 → 构建 → 测试 → 上线。前两个阶段对话式推进，阶段结束由你主动宣布；后续阶段按 SDD 门禁推进。

---

## Phase 0 — 项目初始化

> 一次性准备。技术栈占位符待 Phase 2 方案设计确认后回填，此处只确认项目名。

```
项目初始化检查：
1. 确认 AGENTS.md 中 [PROJECT_NAME] 已替换为实际项目名；技术栈占位符保留，待 Phase 2 方案设计确认后统一回填
2. git init（如尚未初始化；首次 commit 延后到 Phase 2 收尾）
3. 报告确认结果，然后等我发 Phase 1 Prompt
```

## Phase 1 — 需求分析（对话式）

```
我要构建一个 [一句话描述项目]。

先做竞品调研：检索 2-4 个同类竞品（GitHub 开源项目或互联网产品均可），总结每个竞品的定位、核心功能、亮点与不足，以及对我项目的启示（借鉴什么、规避什么、差异化机会）。检索不到明显竞品就如实说明，不强行凑数。

然后进入需求分析对话：围绕目标用户、使用场景、MVP 功能范围、边界与异常、技术约束逐步追问，尽量详细——这个阶段最值得投入时间，一轮不够就多轮，直到需求足够清晰。以自然语言对话，不要弹选项卡片。

需求收敛后，在 .agent/spec.md 中写：
1. 问题陈述：项目解决什么问题
2. 竞品参考：调研结论
3. 目标用户：谁会用
4. MVP 功能列表：每条附验收标准
5. 非目标：明确不做什么
6. 边界与异常：空输入、权限边界、并发冲突等异常场景的期望行为（E 编号）
7. 技术约束：必须满足的限制
8. 假设与依赖

写完给我审阅，我们对话迭代。注意：需求分析阶段是否结束由我主动宣布——我会明确回答"需求分析阶段结束，进入方案设计阶段"；在那之前请持续追问和迭代，不要自行推进。
```

## Phase 2 — 方案设计（对话式）

```
读取 .agent/spec.md，进行方案设计。

以对话式讨论以下内容，不要弹选项卡片：
1. 技术选型：给出候选组合，每个附适用理由与代价/权衡，讨论后定
2. 架构与目录结构：存在多个可行方向时，先对比各自优势与代价，经我确认后再定稿
3. 数据模型：表名 + 字段 + 类型 + 约束 + 关系
4. API 设计：端点列表 + Method + 请求/响应格式，每个端点标注对应的 Fxx，须覆盖全部需求
5. 第三方依赖：包名 + 版本 + 用途

每个重大选择都要附"优势与代价"分析；讨论定稿后在 .agent/plan.md 中写：
1. 技术选型：每个选择附理由与代价/权衡
2. 目录结构：完整文件树
3. 数据模型
4. API 设计
5. 第三方依赖
6. 关键技术决策：同步写入 .agent/decisions.md

写完给我审阅，对话迭代。注意：方案设计阶段是否结束由我主动宣布——我会明确回答"方案设计阶段结束，进入任务拆解"；在那之前请继续讨论和迭代，不要自行推进。

我宣布结束后，请完成收尾：
1. 将确定的技术栈回填 AGENTS.md（替换全部技术栈占位符），代码约定按栈裁剪
2. 新建 README.md：项目名、一句话描述、技术栈
3. decisions.md 追加 D001：技术栈选型决策
4. git commit：chore: init project rules
```

## Phase 3 — 任务拆解

```
读取 .agent/plan.md，拆解实现任务。

在 .agent/tasks.md 中写一个有序清单，格式：
- [ ] T0XX: [任务名] | 依赖: [T0XX或无] | 涉及文件: [路径] | 验收: [标准] | 覆盖: [Fxx/Exx 或 无(基础设施)]

规则：
- 粒度：1 个任务 = 1 个可独立验证的功能点
- 依赖：标注前置任务编号
- 顺序：基础设施数据层 → 核心业务 → API → 辅助 → 测试 → 文档
- 验收：写明怎么验证（运行什么命令、看什么结果）
- 覆盖：每个任务标注它实现的 Fxx 或 Exx；基础设施任务标"无（基础设施）"

拆完自查（确认前逐项检查）：
- 每条 Fxx 至少被一个任务覆盖
- 每条 Exx 有对应的校验或测试任务
- 有缺口先补任务，不要留到 Phase 5

写完让我确认。
```

## Phase 4 — 构建（循环调用）

```
读取 .agent/tasks.md，实现下一个未完成的任务。

要求：
1. 只实现这一个任务，不要超前做后面的
2. 完成后在 tasks.md 中将 [ ] 改为 [x]
3. 在 progress.md 中追加记录（任务编号、文件变更、验证方式）
4. 单独 git commit
5. 告诉我验证方法，等我确认后再做下一个
```

## Phase 5 — 测试与上线

```
所有任务已完成。进行最终验证与交付：

1. 运行全部测试，修复所有报错
2. 逐条对照 .agent/spec.md：MVP 功能（Fxx）是否全部实现
3. 逐条检查「边界与异常」章节（Exx）：异常行为是否符合期望
4. 确认 CI 流水线（本项目为 T012 已配置）正常：push 自动触发 lint + test，CI 状态全绿
5. push 到 GitHub，确认 CI 全绿
6. （可选）配置 CD：main 分支合并后自动部署
7. 更新 README.md：安装步骤、运行方式、API 文档、CI 徽章
8. 在 progress.md 写最终总结

报告：已完成 / 有问题 / 下一步建议。
```

## 上下文恢复 Prompt

> 新会话或会话中断后，用这个 Prompt 让 Agent 快速恢复状态。

```
读取 .agent/ 目录下所有 .md 文件（spec.md、plan.md、tasks.md、progress.md、decisions.md），
理解当前项目状态。

报告：
1. 项目目标（来自 spec.md）
2. 当前处于标准流程哪一步（需求分析 / 方案设计 / 构建 / 测试 / 上线）
3. 已完成的任务（tasks.md 中 [x] 的项）
4. 下一个待执行的任务
5. 有无未解决的问题

等我确认后再继续执行。
```

## 回退 Prompt

> 某个任务出问题，需要回退时使用。

```
任务 [T0XX] 实现有问题，需要回退。

操作：
1. git reset 到 [T0XX] 之前的 commit
2. 在 tasks.md 中将 [T0XX] 改回 [ ]
3. 在 progress.md 中记录回退原因
4. 重新实现 [T0XX]，这次注意 [具体问题]
```

## 需求变更 Prompt

> 构建过程中要新增/修改/删除功能时使用。原则：先改需求规格说明书，再同步下游，最后动代码。

```
我要变更需求：[新增/修改/删除] [Fxx]，内容：[具体描述]。

按以下顺序处理，不要直接改代码：
1. 修订 .agent/spec.md：更新功能列表/边界与异常，状态改回 🔄 待确认
2. 在「变更记录」追加一条：版本号、日期、变更内容、影响范围
3. 列出受影响面（设计说明书章节、tasks.md 任务、已完成代码），同步修订 plan.md 和 tasks.md
4. 已完成但受影响的任务改回 [ ]，并在 progress.md 记录回退原因
5. 给我修订摘要，等我确认后再按 Phase 4 流程执行受影响的任务
```

## 设计变更 Prompt（架构/设计变动）

> 方案设计或构建过程中要调整架构、技术栈、数据模型、模块结构、关键接口时使用。
> 原则：先算账（优势与代价），再确认，后变动。

```
我要调整设计：[描述变动内容，如：把 MySQL 换成 PostgreSQL / 重构某模块结构]。

按以下顺序处理，不要直接改代码：
1. 先在对话中分析这个变动的优势与代价：收益、风险、影响的模块与任务、迁移/重构成本；有备选方案就一并对比
2. 等我主动确认后，才执行变动：
   a. 修订 .agent/plan.md 相关章节，状态改回 🔄 待确认；在「关键技术决策」补充该决策
   b. decisions.md 追加决策记录（选项对比、最终选择、理由）
   c. 同步修订受影响的 tasks.md 任务；已完成且受影响的任务改回 [ ]，并在 progress.md 记录原因
3. 给我修订摘要，等我确认后再继续执行
```
