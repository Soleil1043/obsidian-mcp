# Prompt 模板参考

> 每个阶段对应的 Prompt 模板，直接复制到任意 Agent 对话框使用。
> 将 `[占位符]` 替换为你的实际内容。

---

## Phase 0 — 项目初始化

> 一次性准备，做完即提交，然后进入 Phase 1。

```
项目初始化检查：
1. 确认 AGENTS.md 中 [PROJECT_NAME] 和技术栈占位符已替换为实际内容，未替换则提醒我
2. git init（如尚未初始化），提交规则文件：chore: init project rules
3. 报告确认结果，然后等我发 Phase 1 Prompt
```

## Phase 1 — 需求定义

```
我要构建一个 [一句话描述项目]。

请先问我 3-5 个澄清问题（目标用户、核心功能、MVP 范围、技术约束、边界与异常），
等回答后，在 .agent/spec.md 中写：
1. 问题陈述：项目解决什么问题
2. 目标用户：谁会用
3. MVP 功能列表：每条附验收标准
4. 非目标：明确不做什么
5. 边界与异常：空输入、权限边界、并发冲突等异常场景的期望行为（E 编号）
6. 技术约束：必须满足的限制

写完让我确认，确认后再进入下一步。
```

## Phase 2 — 架构设计

```
读取 .agent/spec.md，设计技术架构。

在 .agent/plan.md 中写：
1. 技术选型：每个选择附一句理由
2. 目录结构：完整文件树
3. 数据模型：表名 + 字段 + 类型 + 约束 + 关系
4. API 设计：端点列表 + Method + 请求/响应格式，每个端点标注对应的 Fxx，须覆盖全部需求
5. 第三方依赖：包名 + 版本 + 用途
6. 关键决策记录：同步写入 .agent/decisions.md

写完让我确认。
```

## Phase 3 — 任务拆解

```
读取 .agent/plan.md，拆解实现任务。

在 .agent/tasks.md 中写一个有序清单，格式：
- [ ] T0XX: [任务名] | 依赖: [T0XX或无] | 涉及文件: [路径] | 验收: [标准] | 覆盖: [Fxx/Exx 或 无(基础设施)]

规则：
- 粒度：1 个任务 = 1 个可独立验证的功能点
- 依赖：标注前置任务编号
- 顺序：基础设施数据层 → 核心业务 → API → 辅助 → 测试 → 文档
- 验收：写明怎么验证（运行什么命令、看什么结果）
- 覆盖：每个任务标注它实现的 Fxx 或 Exx；基础设施任务标"无（基础设施）"

拆完自查（确认前逐项检查）：
- 每条 Fxx 至少被一个任务覆盖
- 每条 Exx 有对应的校验或测试任务
- 有缺口先补任务，不要留到 Phase 5

写完让我确认。
```

## Phase 4 — 逐任务构建（循环调用）

```
读取 .agent/tasks.md，实现下一个未完成的任务。

要求：
1. 只实现这一个任务，不要超前做后面的
2. 完成后在 tasks.md 中将 [ ] 改为 [x]
3. 在 progress.md 中追加记录（任务编号、文件变更、验证方式）
4. 单独 git commit
5. 告诉我验证方法，等我确认后再做下一个
```

## Phase 5 — 验证交付

```
所有任务已完成。进行最终验证：

1. 运行全部测试，修复所有报错
2. 逐条对照 .agent/spec.md：MVP 功能（Fxx）是否全部实现
3. 逐条检查 .agent/spec.md「边界与异常」章节（Exx）：异常行为是否符合期望
4. 确认 CI 流水线（T013 已配置）正常：push 自动触发 lint + test，CI 状态全绿
5. push 到 GitHub，确认 CI 全绿
6. （可选）配置 CD：main 分支合并后自动部署
7. 更新 README.md：安装步骤、运行方式、API 文档、CI 徽章
8. 在 progress.md 写最终总结

报告：已完成 / 有问题 / 下一步建议。
```

## 上下文恢复 Prompt

> 新会话或会话中断后，用这个 Prompt 让 Agent 快速恢复状态。

```
读取 .agent/ 目录下所有 .md 文件（spec.md, plan.md, tasks.md, progress.md, decisions.md），
理解当前项目状态。

报告：
1. 项目目标（来自 spec.md）
2. 已完成的任务（tasks.md 中 [x] 的项）
3. 下一个待执行的任务
4. 有无未解决的问题

等我确认后再继续执行。
```

## 回退 Prompt

> 某个任务出问题，需要回退时使用。

```
任务 [T0XX] 实现有问题，需要回退。

操作：
1. git reset 到 [T0XX] 之前的 commit
2. 在 tasks.md 中将 [T0XX] 改回 [ ]
3. 在 progress.md 中记录回退原因
4. 重新实现 [T0XX]，这次注意 [具体问题]
```

## 需求变更 Prompt

> 构建过程中要新增/修改/删除功能时使用。原则：先改 spec，再同步下游，最后动代码。

```
我要变更需求：[新增/修改/删除] [Fxx]，内容：[具体描述]。

按以下顺序处理，不要直接改代码：
1. 修订 .agent/spec.md：更新功能列表/边界与异常，状态改回 🔄 待确认
2. 在 spec.md「变更记录」追加一条：版本号、日期、变更内容、影响范围
3. 列出受影响面（plan.md 章节、tasks.md 任务、已完成代码），同步修订 plan.md 和 tasks.md
4. 已完成但受影响的任务改回 [ ]，并在 progress.md 记录回退原因
5. 给我修订摘要，等我确认后再按 Phase 4 流程执行受影响的任务
```
